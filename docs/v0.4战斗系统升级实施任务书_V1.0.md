> 前置冻结基线：v0.3.11-stable

# 一、为什么 v0.4 先做战斗

《游戏开发计划书 V1.0》规定的开发顺序中，在第一季剧情骨架与人物关系之后，下一项是：

```text
战斗系统升级
→ 装备与物品系统
→ UI / UX 优化
→ 角色立绘、地图背景、技能特效等美术资源
```

第一季 v0.3 已经正式冻结，因此现在不直接开发第二季，而先完成仍未达到计划目标的战斗系统。

当前战斗已经具备：主角与同行者、主动技能、基础伤害与治疗、敌人回合、胜负、事件战斗结算、动态学会武学进入战斗技能列表。

当前核心缺口：

1. 主角实际等级没有真正换算为战斗属性；
2. 境界没有真正参与战斗；
3. 敌方没有境界数据；
4. 速度没有真正决定行动顺序；
5. 敌人不会使用自己的武学；
6. 没有独立普通攻击；
7. 没有内力 / 能量资源；
8. 武学没有消耗与使用约束；
9. 没有境界压制；
10. 没有通用状态框架；
11. 毒、蛊、控制、护盾等目前只有名字，没有机制；
12. 自动化测试尚未真正覆盖战斗演算。

v0.4 的目标不是“加几个技能”，而是让等级、境界、速度、武学和状态第一次真正进入统一战斗演算。

---

# 二、v0.4 完成边界

必须完成：动态战斗属性、速度行动顺序、普通攻击、基础内力、武学消耗、敌方武学、敌方境界、基础境界压制、通用状态框架、毒/控制/护盾基础形态、基础 AI、战斗自动化回归测试、第一季全流程回归。

不做：正式装备、商店、装备强化、大量丹药、复杂属性克制、超复杂 Boss AI、战斗特效、立绘、技能 CG、大规模 UI 重做、第二季正式剧情、多周目、PVP、联机、自动挂机。

---

# 三、版本策略

冻结基线：`v0.3.11-stable`。

v0.4 开发版本统一使用 `v0.4.x`，全部阶段通过后冻结为 `v0.4.x-stable`。

原则：优先兼容现有 SAVE_VERSION；若必须新增持久化结构，先迁移再发布；每阶段发布前必须通过第一季 smoke test。

---

# 四、战斗设计原则

- 战斗力影响难度，但等级/境界不替代声望和剧情推进。
- 境界压制明显但不绝对，必须保留越级可能。
- 武学不能都只是不同倍率攻击；招式、内功、奇术/蛊术、治疗应逐步体现差异。
- 角色、敌人、武学、境界和状态参数优先数据驱动，不在 app.js 写角色专用战斗分支。

---

# 五、阶段 A：战斗基线审计与回归锁

目标：在动算法前锁住 v0.3.11-stable 当前战斗行为。

任务：

- 记录 `createBattle()`、`useSkill()`、胜负和事件回传；
- 建立独立 battle smoke / unit test；
- 覆盖 1v1、2v2、治疗、玩家新学武学、胜利、失败；
- 第一季 `season1-smoke.mjs` 继续通过；
- 不改变实际战斗玩法。

完成标志：当前战斗行为被自动测试锁住。

---

# 六、阶段 B：动态战斗属性

建立统一 combatant 构造层，使主角真实读取 player.level、player.realm、基础角色属性和已学武学；等级至少影响最大气血、攻击、防御、少量速度；境界提供基础属性系数、内力上限和 realm order。

完成标志：Lv.1 与 Lv.6、不同境界进入战斗时属性出现可验证差异。

---

# 七、阶段 C：统一行动顺序与普通攻击

所有存活单位按有效速度统一排序行动；速度真正影响先后。新增无需内力的普通攻击，成为最低成本动作。

完成标志：高速敌人可以在低速玩家之前行动，修改速度会改变顺序。

---

# 八、阶段 D：内力与武学消耗

战斗单位增加 `maxQi / qi`；武学数据支持 `qiCost`；普通攻击 0 消耗，强力武学更高消耗；内力不足不能施放；战斗 UI 显示气血与内力。

完成标志：玩家不能无限连续释放最强武学，需要做资源选择。

---

# 九、阶段 E：敌方境界、武学与基础 AI

敌人增加 realm、skills、内力和基础 AI 数据。AI 至少会：有资源时择机用技能、内力不足普通攻击、有治疗时低血量考虑治疗。

完成标志：探子、力士、黑无常、焦兰殿禁卫出现实际战斗方式差异。

---

# 十、阶段 F：境界压制基础版

境界差值温和影响伤害、减伤、有效速度与控制抗性接口；禁止绝对秒杀或完全免伤。

完成标志：只改变境界时，战斗伤害和结果出现稳定合理差异。

---

# 十一、阶段 G：通用状态框架

状态对象至少包含 id、name、duration、source、stacks。

v0.4 必须至少落地：

- 中毒：持续掉血；
- 一种控制：跳过一次行动；
- 护盾：优先吸收伤害。

完成标志：三类状态均能由技能施加、回合中生效、正确到期、写入可读日志且不破坏事件结算。

---

# 十二、阶段 H：武学与熟练度进入战斗计算

mastery 对武学产生温和实际效果；已有 realmRequirement 必须在战斗中真正校验。

完成标志：【折风剑式】Lv.2 与 Lv.1 有可测但不过度的差异，境界要求生效。

---

# 十三、阶段 I：战斗 UI 最小适配

只改战斗相关 UI，不做全游戏 UI 重做。

必须清楚显示：单位名称、气血、内力、境界、当前行动者、技能名与消耗、不可使用原因、关键状态、胜负与战斗日志。

完成标志：手机上能清楚理解谁行动、还有多少血/内力、为什么技能不能用、有哪些状态。

---

# 十四、阶段 J：战斗自动化测试与第一季回归

新增测试至少覆盖：动态属性、速度顺序、普通攻击、内力、敌方技能与 AI、境界压制、中毒、控制、护盾、治疗、动态武学、熟练度、胜利和失败。

GitHub Actions 固定为：

```text
静态检查
→ manifest 检查
→ battle smoke
→ season1 smoke
→ Pages 部署
```

任一失败禁止发布。

# 十五、阶段 K：v0.4 真机总验收与冻结

旧存档必须保持人物关系、武学、折风剑式熟练度、第一季完成状态；新存档仍可完成第一季；真机确认普通攻击、内力、速度、境界压制、敌方技能、状态和战果结算。

全部通过后冻结为 `v0.4.x-stable`，并建立 `docs/v0.4战斗系统验收冻结报告.md`。

# 最终判定

v0.4 不是“把伤害数字调得更复杂”。

真正完成标准是：玩家的等级、境界、速度、武学与状态第一次统一进入战斗演算；敌人也拥有境界、武学和基本行为差异；这套底层能够继续承载第二季至第七季，而不需要每新增一个角色或敌人就改写核心战斗代码。

只有达到这一标准，才允许按照上位计划进入下一顺位：**装备与物品系统。**
