# 《不良人：江湖行》v0.2 技术实施任务书

> 文档性质：开发执行文档  
> 上位依据：《不良人：江湖行》游戏开发计划书 V1.0  
> 当前基线：Prototype v0.1  
> v0.2 目标：将现有技术原型升级为可长期承载第一季至第七季内容的“群侠传式江湖 RPG 基础框架”。

---

## 0. 本阶段总原则

v0.2 暂时不追求大量剧情、美术和特效。

本阶段只解决一个问题：

**以后增加一季剧情、一个人物、一门武学、一个隐藏事件时，应当主要增加数据，而不是反复修改底层代码。**

必须坚持：

1. 声望、等级、境界、修为、人物好感彼此独立。
2. 主线与隐藏剧情使用通用事件引擎触发。
3. 角色、武学、地点、事件尽量数据驱动。
4. 存档必须版本化，并允许从 v0.1 平滑迁移。
5. 手机 PWA 更新机制必须可靠。
6. 当前可运行的 v0.1 保留为回退基线。
7. 第一季大规模填剧情之前，先通过少量测试事件验证框架。

# 一、现有 v0.1 技术审计

当前项目已经拥有：

- GitHub Pages 自动部署
- PWA 安装
- LocalStorage 本地存档
- 节点式世界地图
- 队伍页面
- 武学页面
- 行囊页面
- 江湖记录
- 简单回合制战斗
- 基础角色、武学、敌人和地图数据

现有代码仍属于原型结构，主要问题如下。

## 1. 存档结构过于扁平

当前存档主要包含 level、exp、silver、stamina、party、flags、quest、logs、mastery。

问题：

- 没有声望。
- 没有修为。
- 没有境界。
- 没有人物好感。
- 没有章节 / 季度进度模型。
- 没有正式物品背包数据。
- 没有事件完成记录。
- 没有数据迁移机制。
- 读取存档只是浅层合并，未来嵌套字段增加后存在兼容风险。

## 2. 剧情逻辑写死在 app.js

目前“城南驿道”“藏兵谷暗记”等内容直接由按钮事件处理。

这种模式如果扩展到七季，会导致：

- app.js 极度膨胀。
- 一个剧情修改可能影响大量界面代码。
- 隐藏条件越来越难维护。
- 很难检查剧情互斥与前置条件。

v0.2 必须将剧情从 UI 逻辑中抽离。

## 3. 地点解锁逻辑直接写在数据函数里

现状类似：

- scoutDefeated → 藏兵谷
- chapter1Done → 岐国

未来需要改为统一条件系统。

## 4. 人物锁定是静态字段

女帝、降臣目前只是 `locked: true`。

v0.2 后必须由玩家状态决定：

- 是否认识
- 是否可互动
- 是否可同行
- 好感
- 专属剧情进度
- 当前关系状态

## 5. PWA 更新机制需要升级

当前 Service Worker 是缓存优先模式。

风险：

- GitHub 已经更新，但手机可能继续读取旧 JS/CSS。
- 用户关闭重开也不一定立刻得到最新版本。

v0.2 第一阶段必须解决。

# 三、v0.2 标准玩家状态模型

建议将存档升级到 `saveVersion: 2`。

参考结构：

```js
{
  saveVersion: 2,
  gameVersion: "0.2.0",
  player: {
    name: "无名少侠",
    level: 1,
    exp: 0,
    cultivation: 0,
    realm: "unranked",
    silver: 120,
    stamina: 40,
    maxStamina: 40
  },
  world: {
    season: 1,
    chapter: "s1_prologue",
    reputation: 0,
    unlockedLocations: ["yuzhou"],
    flags: {}
  },
  relationships: {
    chimeng: { met: true, affinity: 20, relationStage: "acquainted" },
    nvdi: { met: false, affinity: 0, relationStage: "unknown" },
    jiangchen: { met: false, affinity: 0, relationStage: "unknown" }
  },
  party: ["player", "chimeng"],
  martialArts: {
    basic_sword: { learned: true, mastery: 1, exp: 0 }
  },
  inventory: {
    items: { healing_powder: 3, old_coin: 1 },
    equipment: { weapon: null, armor: null, accessory: null }
  },
  events: { completed: [], failed: [], active: [], counters: {} },
  logs: [],
  meta: { createdAt: 0, savedAt: 0, playCount: 1 }
}
```

这是逻辑结构，不要求字段名称百分之百固定，但后续开发必须保持同等层次。

# 四、等级系统

等级负责基础成长，不负责剧情推进。

基础字段：`player.level`、`player.exp`。

v0.2 要实现：战斗结算增加经验；达到阈值后自动升级；升级增加少量基础属性；UI 显示当前等级和升级进度；等级不能直接触发“第一季 → 第二季”。

验收标准：新存档从 Lv.1 开始；战斗获得经验；经验达到要求自动升级；重新打开游戏等级保持；等级变化不会错误修改声望或境界。

---

# 五、声望系统

声望是世界事件与主线大事件的主要推进变量，字段为 `world.reputation`。

建议统一提供：`addReputation(amount, reason)`、`setReputation(value)`、`getReputationRank()`。

声望来源包括主线、支线、江湖挑战、救人、击败知名敌人和特殊选择。声望不是善恶值。

v0.2 测试阈值：0 无名小卒；50 小有名气；100 江湖新秀；200 声名渐起。

验收标准：事件能奖励声望；世界页能看到声望；声望达到阈值后测试事件自动满足；不足时不出现；变化写入江湖记录。

---

# 六、修为与境界系统

正式境界：

```text
无品 → 小星位 → 中星位 → 大星位 → 小天位 → 中天位 → 大天位 → 神霄位
```

内部 ID 建议：`unranked`、`small_star`、`middle_star`、`great_star`、`small_heaven`、`middle_heaven`、`great_heaven`、`shenxiao`。

建立 `realms.js`，每个境界至少包含 id、name、order、cultivationRequired、statMultiplier、description。

v0.2 修为来源先支持战斗、练功、特殊事件。前期修为足够即可突破；后期允许附加武学、道具、事件条件。

验收标准：新存档无品；修为能增长；达到阈值可突破小星位；突破后保存正常；UI 同时显示等级和境界；两者互不替代。

---

# 七、人物关系系统

每个重要人物至少维护：`met`、`affinity`、`relationStage`、`personalFlags`。

好感建议范围 -100～100。界面可显示敌视、冷淡、初识、熟悉、信任、亲近等阶段。同行与好感必须分开。

验收标准：蚩梦存在初始关系；女帝、降臣未见过也有标准关系对象；事件能改变好感；好感能参与事件条件；变化能保存。

---

# 八、通用条件系统

建立 `conditions.js`。事件、地点、人物互动全部使用统一条件判断。

第一批必须支持：`reputationGte`、`reputationLte`、`levelGte`、`realmGte`、`cultivationGte`、`flagTrue`、`flagFalse`、`eventCompleted`、`eventNotCompleted`、`affinityGte`、`affinityLte`、`hasItem`、`locationUnlocked`、`seasonIs`、`chapterIs`。

提供：`checkCondition(condition, state)`、`checkConditions(conditions, state)`。

原则：UI 不允许自己另外写一套剧情条件。

---

# 九、通用事件引擎

这是 v0.2 最重要的模块。建立 `events.js`。

事件类型至少支持：main、side、hidden、character、encounter。

事件结果至少支持：增加经验、修为、声望、银两、好感；获得/失去物品；设置 Flag；解锁地点；开始战斗；标记完成/失败；修改章节。

核心接口：`getAvailableEvents(state, locationId)`、`completeEvent(eventId, result)`。

地图打开某地点时，应先通过事件引擎查找当前可用事件，再渲染按钮，不再在 app.js 中硬编码剧情按钮和奖励。

---

# 十、剧情 Flag 规范

Flag 只能表示无法被其它结构清晰表达的世界事实，例如 `helped_huanyinfang`、`spared_xuanming_scout`、`found_dragon_spring_clue`。

禁止使用 `story1`、`step4`、`doneA` 等无语义名称。

事件是否完成用 events.completed；人物是否认识用 relationships；地点是否解锁用 unlockedLocations；当前章节用 world.chapter，不重复建 Flag。

---

# 十一、章节与七季结构

字段：`world.season`、`world.chapter`。

第一季暂定骨架：`s1_prologue`、`s1_yuzhou`、`s1_xuanming`、`s1_huanyinfang`、`s1_tongwenguan`、`s1_longquan`、`s1_finale`。

chapter 只是当前世界阶段，不代表玩家只能做一个主线任务。同一阶段可同时存在主线、人物事件、支线、隐藏事件和江湖活动。

---

# 十二、武学系统 v0.2

现有 mastery 升级为玩家状态中的 martialArts，每门武学至少包含 learned、mastery、exp。

武学数据至少提供 id、name、category、description、power、realmRequirement、masteryMax。分类统一为内功、招式、身法、奇术。

本阶段只保证武学属于玩家状态、可以升级熟练度、可以有境界要求，并给未来残篇/传授机制留接口。

---

# 十三、地点系统 v0.2

大型地图建议由事件显式解锁，特殊入口允许条件判断。原则：**大型地图采用显式解锁；特殊入口使用条件判断。**

---

# 十四、战斗系统 v0.2 边界

本轮不重写完整战斗系统，只做新框架接口改造。

必须支持：战斗由事件启动；胜负回传事件引擎；奖励不再写死在 `finishBattle()`；敌人增加境界；速度参与基础行动顺序。

毒、蛊、控制、护盾、连携、内力消耗等高级内容可后移。

---

# 十五、物品与装备 v0.2 边界

现有 ITEMS 从展示数据改为真实背包状态。本阶段只实现获得、失去、数量变化、物品条件检查和装备槽数据结构。药品战斗内使用、装备属性计算可后移。

---

# 十六、存档迁移

建立 `migrateSave(rawSave)`。

流程：读取 LocalStorage → 判断 saveVersion → v1 迁移 v2 → 补齐字段 → 校验结构 → 保存 v2。

v1 → v2 最低迁移要求：保留等级、经验、银两、队伍、已完成序章关键状态、武学熟练度和江湖记录。新增字段使用合理默认值。异常存档不能让游戏永久白屏。

验收标准：新安装正常创建 v2；模拟 v1 能打开；关键进度不无故丢失；新字段补齐；错误存档有安全回退。

---

# 十七、PWA 自动更新

这是 v0.2 第一批必须完成的技术修复。

目标：**GitHub 更新 → Pages 发布 → 用户重新打开游戏后尽快得到新版。**

Service Worker 调整方向：增加缓存版本；install 使用 `skipWaiting()`；activate 使用 `clients.claim()`；HTML/JS/CSS 优先网络更新；离线时读取缓存；清理旧缓存。

建立统一版本常量：`GAME_VERSION = "0.2.0"`。

验收标准：发布 v0.2.0 手机能看到；再发布 v0.2.1 后关闭重开能切换；无网络仍能打开已缓存游戏；不需要手动清缓存。

# 二十、实施阶段划分

## 阶段 A：安全基线与更新机制

保留 v0.1 回退基线；加统一版本常量；重做 Service Worker；验证 Pages 发布后手机更新。

完成标志：**手机明确显示 v0.2.0，后续测试版本能自动刷新。**

## 阶段 B：State v2 + 存档迁移

建立嵌套状态模型、saveVersion、v1→v2 迁移并改造旧字段引用。

完成标志：**旧存档和新存档均可打开，不白屏。**

## 阶段 C：成长系统

完成等级、经验、修为、境界、声望。

完成标志：**测试战斗可同时获得经验、修为和声望，并正常升级/突破。**

## 阶段 D：人物关系

完成 relationships、好感变化、关系阶段、同行与关系解耦。

完成标志：**一个事件可以让蚩梦好感变化，并正确影响后续事件。**

## 阶段 E：条件与事件引擎

完成 conditions.js、events.js、通用奖励/效果处理、地点自动列出可用事件。

完成标志：**不修改 app.js 主流程，仅增加事件数据，就能新增一个隐藏事件。**

## 阶段 F：现有序章迁移

把驿道疑云、玄冥教探子、藏兵谷、石壁暗记、玄冥教力士迁入事件系统。

完成标志：**现有 v0.1 内容仍能游玩，但 app.js 不再写死剧情结算。**

## 阶段 G：第一季骨架

建立 s1_prologue → s1_yuzhou → s1_xuanming → s1_huanyinfang → s1_tongwenguan → s1_longquan → s1_finale。

只放大事件节点、解锁关系、少量测试对白、条件、奖励和世界状态变化。

完成标志：**第一季从序章到终局骨架可以完整跑通。**

## 阶段 H：v0.2 验收与冻结

完成全部验收后定为 `v0.2.x stable`，之后进入第一季正式内容填充。

# 二十三、代码完成标准

每次提交至少满足：JavaScript 语法检查通过；首页启动；存档读取无报错；核心流程无明显回归；移动端按钮可点击；旧存档不因新增字段白屏；GitHub Actions / Pages 发布成功。

1. 建立统一 `GAME_VERSION = "0.2.0"`。
2. 重构 `sw.js`，解决手机缓存旧版本问题。
3. 建立 State v2 数据模型。
4. 建立 v1 → v2 存档迁移。
5. 页面展示版本、等级、境界、声望。

v0.2 不是“内容更多的 v0.1”。
