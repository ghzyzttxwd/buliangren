# 一、上位计划约束

《游戏开发计划书 V1.0》的严格开发顺序为：

```text
战斗系统升级
→ 装备与物品系统
→ UI / UX 优化
→ 角色立绘、地图背景、技能特效等美术资源
```

装备系统原则：

- 保持克制；
- 装备槽以武器 / 衣甲 / 饰品为主；
- 重要物品包括武学秘籍、残卷、丹药、剧情道具、宝物、特殊材料；
- 不采用“白装 → 蓝装 → 紫装 → 橙装”的传统网游品阶体系；
- 更强调物品自身的身份、来源与特殊作用。

因此 v0.5 不追求刷装备，而是让每件物品真正成为江湖内容的一部分。

# 二、现状审计

## 已有底层

State v2 已存在：

```js
inventory: {
  items: {
    healing_powder: 3,
    old_coin: 1,
    cloth_bracer: 1
  },
  equipment: {
    weapon: null,
    armor: null,
    accessory: null
  }
}
```

现有系统还已经支持：

- 物品数量持久化；
- 旧存档补齐 inventory；
- `hasItem` 条件；
- 事件层已有物品获得 / 消耗的基础接口方向；
- v0.4 战斗属性统一从 combatant 构造层进入战斗。

## 当前缺口

1. `data.js` 的 ITEMS 仍是展示数组，没有稳定 item id 数据模型；
2. 行囊 UI 读取静态 ITEMS，而不是 `state.inventory.items`；
3. 装备槽存在，但没有装备 / 卸下操作；
4. 装备属性不参与 `buildPlayerCombatant()`；
5. 止血散等消耗品不能实际使用；
6. 战斗中不能使用物品；
7. 秘籍 / 残卷 / 剧情物 / 宝物 / 材料没有统一类型语义；
8. 没有基本商人 / 购买接口；
9. 没有 inventory smoke test；
10. 第一季旧档虽然保存了物品结构，但当前 UI 基本无法证明它被真实使用。

因此 v0.5 的核心不是“增加一堆道具”，而是：

> **让物品从存档字段和展示卡片，升级成真正参与成长、战斗、事件和经济循环的数据系统。**

# 四、数据设计原则

## 1. 稳定 item id

物品数据改为以 id 为核心，例如：

```js
ITEMS = {
  healing_powder: {
    id: 'healing_powder',
    name: '止血散',
    category: 'consumable'
  }
}
```

State 仍只保存：

```text
itemId → count
```

不把整份静态物品定义复制进存档。

## 2. 物品类型

v0.5 统一支持：

- `equipment`
- `consumable`
- `manual`
- `fragment`
- `quest`
- `treasure`
- `material`

不要求每类马上塞大量内容，但接口必须明确。

## 3. 装备槽

只保留现有三槽：

```text
weapon
armor
accessory
```

本阶段只给主角装备。

## 4. 装备属性

第一版只允许清晰、可控的基础修正，例如：

- attack
- defense
- speed
- maxHp
- maxQi

允许少量明确特殊效果预留字段，但不在 v0.5 大规模扩展。

## 5. 物品有身份，不走刷装路线

装备与宝物的价值来自：

- 来源；
- 名称；
- 剧情意义；
- 明确属性；
- 特殊用途。

禁止以随机品质颜色作为主要价值来源。

# 六、阶段 B：统一物品数据目录

## 目标

把当前静态展示型 ITEMS 改为稳定 id 驱动的 item catalog。

每件物品至少支持：

```text
id
name
category
description
stackable
```

装备追加：

```text
slot

```

消耗品追加：

```text
useContext
effects
```

可选补充：

```text
price
sellPrice
unique
```

## 兼容要求

必须保留并正式定义现有：

- `healing_powder`
- `old_coin`
- `cloth_bracer`

不因数据重构删除旧存档已有物品。

## 完成标志

所有行囊内容均可通过 item id 从目录解析，不再依赖 UI 写死名称和数量。

# 七、阶段 C：真实行囊 UI

## 目标

行囊页面改为读取：

```text
state.inventory.items
```

而不是静态 ITEMS.count。

## 必须显示

- 物品名称；
- 类型；
- 当前数量；
- 描述；
- 装备槽 / 属性（装备类）；
- 是否已装备；
- 是否可使用；
- 剧情道具等不可使用时不显示假按钮。

## 手机要求

- 数量变化后立即刷新；
- 不横向溢出；
- 物品较多时可以正常滚动；
- 不进行全局 UI 重做。

## 完成标志

存档中的真实物品数量与行囊页面完全一致。

---

# 八、阶段 D：装备 / 卸下

## 目标

正式启用现有：

```text
weapon / armor / accessory
```

三槽。

## 必须实现

- 装备；
- 卸下；
- 同槽替换；
- 非装备不能进入装备槽；
- slot 不匹配不能装备；
- 未拥有的物品不能装备；
- 已装备物品仍属于玩家，不额外复制数量。

## 状态原则

`inventory.items` 表示所有权；
`inventory.equipment` 只记录当前装备的 item id。

## 完成标志

保存、关闭、重新打开后，装备状态保持正确。

# 九、阶段 E：装备属性进入战斗

## 目标

装备属性通过 v0.4 已冻结的 combatant 构造层进入战斗，而不是直接写死进 `battle.js`。

优先修改：

```text

```

统一合并：

```text

```

## 第一版至少验证

- 攻击装备改变 attack；
- 防御装备改变 defense；
- 速度装备可改变行动顺序；
- HP / 内力类装备正确改变上限；
- 卸下后属性恢复；
- v0.4 境界压制、内力、状态、熟练度逻辑不被改写。

## 完成标志

装备第一次真实影响战斗结果。

# 十、阶段 F：消耗品正式使用

## 目标

让止血散等消耗品从“描述物品”变成真实可用资源。

## 战斗外

至少支持一种：

```text
恢复状态 / 资源
→ 数量 -1
→ 自动保存
```

## 战斗内

至少支持一种战斗物品动作。

规则：

- 使用物品占用当前角色一次行动；
- 数量真实扣除；
- 数量为 0 不能使用；
- 不允许无限使用已耗尽物品；
- 效果走通用 item effect，不按具体物品名写死在 app.js。

第一版不做复杂丹药 Buff 链。

## 完成标志

止血散等基础消耗品可被真实消耗并产生效果，存档数量同步变化。

# 十一、阶段 G：秘籍、残卷与特殊物品语义

## 目标

让高层计划中的重要物品类型具有明确系统语义。

可以配置：


### 材料 `material`

先完成分类和持有，不提前做锻造系统。

## 完成标志

系统能够区分“能吃的药、能装备的物、能学武学的秘籍、只能用于剧情的道具”。

# 十二、阶段 H：基础商人与银两循环

## 目标

建立最小商人购买框架，解决银两长期只有奖励、缺少稳定用途的问题。

## 第一版只要求

- 商人商品列表由数据配置；
- 显示价格；
- 银两足够才能购买；
- 购买后银两扣除；
- 物品数量增加；
- 银两不足明确提示；
- 剧情道具 / 唯一宝物不能被普通商店无限购买。

## 边界

本阶段默认只做“购买”。

出售系统如无必要可后移，避免同时引入复杂经济平衡。

商人入口不得改变第一季主线事件条件与历史节点。

## 完成标志

银两形成最小的“获得 → 消费 → 获得物品”闭环。

# 最终判定

v0.5 的完成标准不是“背包里多了很多东西”。

真正完成标准是：

> **物品拥有稳定身份和真实数量；装备可以实际穿戴并参与战斗；消耗品可以真实使用；秘籍、残卷、剧情道具、宝物和材料具有清晰语义；银两拥有基本消费出口，而且这一切继续通过数据扩展，不需要为每件物品改写核心代码。**

只有达到这一标准，才允许按照上位计划进入下一顺位：

**UI / UX 优化。**
